# 联邦查询
* 联邦查询（Federated Query）是一种数据查询技术，它允许用户通过`单一的查询接口`，对`分布在不同数据源`（可能位于不同位置、属于不同系统或采用不同数据格式）中的数据进行`统一查询`，而`无需`将这些数据物理`集中到一个数据库中`。


工作原理
联邦查询的过程通常包括以下步骤：

1、`查询解析`：解析用户提交的查询语句，确定需要访问的数据源和数据范围。
2、数据源映射：将查询中的逻辑表或字段映射到底层数据源的实际表和字段（需预先定义数据源的元数据和映射关系）。
3、查询优化：生成最优执行计划，例如决定哪些子查询在本地执行、哪些推送到远程数据源（减少数据传输量）。
4、`查询分发`：将优化后的子查询分发到`对应的数据源`执行（可能需要适配不同数据源的查询语言，如将 SQL 转换为 NoSQL 的查询语法）。
5、`结果聚合`：收集各数据源返回的结果，进行合并、关联或计算，最终返回统一的结果给用户。

## mindsdb联邦查询案例
* mindsdb是自己内部实现的联邦查询引擎,但是步骤是一样的

#### 创建数据库表

1、postgres
```
-- 登录PostgreSQL（默认用户postgres）
psql -U postgres

-- 创建数据库（命名为pg_chatbi）
CREATE DATABASE pg_chatbi;

-- 切换到新数据库
\c pg_chatbi;

-- 用户表（核心关联表，通过user_id关联MySQL）
CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,  -- 自增主键，与MySQL的user_id关联
    username VARCHAR(50) UNIQUE NOT NULL,  -- 用户名
    register_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP  -- 注册时间
);

-- 插入测试数据
INSERT INTO users (username) VALUES
('alice'),
('bob'),
('charlie');

-- 订单表（关联users表的user_id）
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    user_id INT NOT NULL REFERENCES users(user_id),  -- 关联当前库的用户
    product_name VARCHAR(100) NOT NULL,  -- 商品名称
    order_amount DECIMAL(10,2) NOT NULL,  -- 订单金额
    order_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 插入测试数据（用户1、2有订单）
INSERT INTO orders (user_id, product_name, order_amount) VALUES
(1, 'PostgreSQL实战指南', 59.99),
(2, '数据库优化手册', 79.99),
(1, 'Python编程入门', 45.00);
```

2、MySQL
```
-- 登录MySQL（默认用户root）
mysql -u root -p

-- 创建数据库（命名为mysql_chatbi）
CREATE DATABASE mysql_chatbi CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 切换到新数据库
USE mysql_chatbi;

-- 用户详情表（关联PostgreSQL的users.user_id）
CREATE TABLE user_profiles (
    profile_id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT UNIQUE NOT NULL,  -- 与PostgreSQL的user_id保持一致（核心关联字段）
    email VARCHAR(100) UNIQUE NOT NULL,  -- 邮箱
    phone VARCHAR(20) UNIQUE,  -- 手机号
    address TEXT  -- 地址
);

-- 插入测试数据（user_id与PostgreSQL的users表对应）
INSERT INTO user_profiles (user_id, email, phone, address) VALUES
(1, 'alice@example.com', '13800138001', '北京市海淀区'),
(2, 'bob@example.com', '13900139001', '上海市浦东新区'),
(3, 'charlie@example.com', '13700137001', '广州市天河区');

-- 支付表（关联user_profiles的user_id，即关联PostgreSQL的用户）
CREATE TABLE payments (
    payment_id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,  -- 关联当前库的user_profiles.user_id（即PostgreSQL的user_id）
    payment_amount DECIMAL(10,2) NOT NULL,  -- 支付金额
    payment_method VARCHAR(20) NOT NULL,  -- 支付方式（微信/支付宝）
    payment_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES user_profiles(user_id)
);

-- 插入测试数据（用户1、3有支付记录）
INSERT INTO payments (user_id, payment_amount, payment_method) VALUES
(1, 59.99, 'wechat'),
(1, 45.00, 'alipay'),
(3, 120.00, 'wechat');


```
* 关联关系说明:
* 核心关联字段：PostgreSQL 的users.user_id ↔ MySQL 的user_profiles.user_id（一对一关联）。
* 跨库关联场景：
PostgreSQL 存储用户基本信息（users）和订单数据（orders）。
MySQL 存储用户详细信息（user_profiles）和支付数据（payments）。

* 询问agent, 问题:`用户 “alice” 在 PostgreSQL 中有一笔 45 元的订单，对应的 MySQL 支付记录的支付方式是什么？`

* 这个 Agent 的思考和操作过程展示了它如何解决 "找出在 MySQL 用户表中存在但在 PostgreSQL 订单表中没有订单记录的用户 ID" 这一问题，具体过程如下：

1、初始尝试：
Agent 首先尝试直接使用跨库的 NOT EXISTS 子查询，想一次性找出符合条件的用户
但出现了错误：PostgreSQL 数据库中无法识别 MySQL 表的别名 "up"，因为跨库查询时表引用需要特殊处理
2、问题分析：
Agent 意识到错误原因是跨数据库引用的处理问题
决定采取分步查询策略，先分别获取两个库的数据，再进行比对
3、分步查询：
第一步：从 MySQL 的 user_profiles 表获取所有用户 ID（结果是 1、2、3）
第二步：从 PostgreSQL 的 orders 表获取有订单记录的用户 ID（结果是 1、2）
4、最终查询：
`使用 NOT IN 子查询，将前两步的结果结合起来(联邦查询的结果聚合步骤)`
从 MySQL 的所有用户中排除那些在 PostgreSQL 有订单记录的用户
最终得到结果：用户 ID 为 3 的用户在 MySQL 中存在，但在 PostgreSQL 中没有订单记录

* `这一步就是通过查询引擎屏蔽不同数据库的差异，将跨库子查询的结果作为临时数据集在内存中进行关联计算，从而让用户可以像操作单库一样编写跨库查询逻辑。`

* `not in里面的子查询的确是pgsql执行的,但是会存在内存数据集中,等于屏蔽了不同数据库的差异,等于not in成功返回了,从而使得整个sql查询成功`
